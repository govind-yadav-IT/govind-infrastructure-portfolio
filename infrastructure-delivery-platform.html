Objective

The objective was to build a practical infrastructure delivery workflow that connects infrastructure provisioning, containerized application hosting, and deployment automation.

Problem addressed

Deploying an application involves more than writing code. The host must exist, the application must run consistently, the web server must serve the right files, and there should be a way to verify that the deployment is healthy. This project brings those pieces into one workflow.

Architecture

The workflow is structured around an AWS EC2 host running Docker Compose. GitHub Actions provides the automation layer, while a Bash health-check script verifies the local application and uploads its log to Amazon S3.

Implementation

  • Terraform-based AWS provisioning: the project is intended to provision the EC2 hosting environment through Terraform.
  • Docker Compose and Nginx: a docker-compose.yml file defines an Nginx service named portfolio-web, exposes port 80, mounts the html/ directory read-only into Nginx’s web root, and restarts the container automatically.
  • GitHub Actions deployment: the repository contains .github/workflows/deploy.yml, which represents the deployment automation entry point.
  • Bash health check: Scripts/health-check.sh uses curl against http://localhost, records a timestamped HEALTHY or UNHEALTHY result, appends it to a local log, and copies the log to an S3 bucket.
  • Static application content: html/index.html provides the content served by Nginx.
version: "3.8"
services:
  webserver:
    image: nginx:latest
    container_name: portfolio-web
    ports:
      - "80:80"
    volumes:
      - ./html:/usr/share/nginx/html:ro
    restart: always

Technical decisions

  • Nginx is used as a lightweight web server for static content.
  • The HTML directory is mounted read-only, separating application content from the container image.
  • restart: always makes the container restart automatically after host or container restarts.
  • The health check writes a timestamped record rather than only printing a status, making the result easier to retain and review.
  • S3 provides durable storage for the health log outside the EC2 host.

What I learned

This project helped me connect several infrastructure concepts: provisioning, container configuration, port mapping, volume mounts, deployment automation, and post-deployment verification. It also showed that a deployment is not complete simply because a container starts; the served endpoint needs to be checked.

Current limitations

  • This is a learning project, not a production platform.
  • The health-check script assumes that its log directory already exists.
  • It assumes AWS CLI credentials and S3 permissions are configured on the host.
  • Repository-level evidence for CloudWatch alarms, cron scheduling, and the complete Terraform resource set could not be independently verified in this build, so those items should be confirmed against the repository before being presented as implemented features.

Future improvements

  • Add explicit health-check configuration to Docker Compose.
  • Use structured logging and retention policies for health records.
  • Add automated Terraform validation and plan output in CI.
  • Expand monitoring beyond a single local HTTP check.
